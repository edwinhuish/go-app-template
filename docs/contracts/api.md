# 接口契约（前后端公共约定）

**这份文件是接口协议与错误码的唯一正本。** 它是框架侧的评审与对照基准：
形状、码表、字段名先在这里定稿，看 diff 只看这一份。

两端各自的 `AGENTS.md` 会**内联一份必要摘要**——不是抄，而是因为端级文档必须自包含
（不得外链到本文件，详见 [`../../AGENTS.md`](../../AGENTS.md) 第 2 节）。所以这类信息一共三处：

- `docs/contracts/api.md`（本文件，正本）
- `apps/server/AGENTS.md`（后端要实现的那份）
- `apps/web/AGENTS.md`（前端要消费的那份）

- 后端规范：[`../../apps/server/AGENTS.md`](../../apps/server/AGENTS.md)
- 前端规范：[`../../apps/web/AGENTS.md`](../../apps/web/AGENTS.md)
- 跨端全景与文档地图：[`../architecture.md`](../architecture.md)

改契约的流程见文末「变更流程」。三处冲突时**以本文件为准**，并视为文档 bug：
当次改动顺手修正端级摘要里的那一句（端级摘要反过来不能要求本文件「见某某规范」）。

## 1. 传输层

| 项 | 约定 |
|---|---|
| 前缀 | 所有业务接口挂在 `/api/v1` 下（路由组 `router.go`，前端 `constants/index.ts` 的 `API_BASE`） |
| 方法 | 只用 `GET/POST/PUT/DELETE`；`PUT` 是全量覆盖，省略的字段按清空处理（想要局部更新就换 `PATCH` 或先读后写） |
| 请求体 | `application/json`；唯一例外是 `FormData` 上传，由客户端跳过 `Content-Type` 注入 |
| 鉴权头 | `Authorization: Bearer <token>`；无令牌 / 令牌失效一律 401 |
| 请求 ID | `X-Request-ID`，前端可不传；后端必生成并写回响应头与响应体 |
| 开发期代理 | Vite 把 `/api` 代理到 `127.0.0.1:8080`，前端代码里永远用相对路径 |

## 2. 响应体

所有接口（含错误）只有一种形状：

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "request_id": "0f3c1a7e9b2d4c55"
}
```

| 字段 | 说明 |
|---|---|
| `code` | 业务码，`0` 表示成功，非 `0` 见第 3 节 |
| `message` | 给人看的文案，前端可直接展示；成功时**恒为 `ok`**（新建与查询的差别看 HTTP 状态码 201/200，不看文案） |
| `data` | 业务数据；失败时**省略**（`omitempty`），前端按 `code` 分支，不要读 `data` |
| `request_id` | 与 `X-Request-ID` 一致，排查问题时让用户报这个值 |

状态码与业务码同时存在，但**只由业务码推导**：成功 `200`（新建 `201`），失败取
`code / 100` 的前三位。不要在 handler 里为某个错误单独挑状态码。

## 3. 业务错误码

| code | HTTP | 语义 | 典型场景 |
|---|---|---|---|
| `0` | 200 / 201 | 成功 | — |
| `40001` | 400 | 参数错误 | 绑定失败、业务校验不通过、文案由 service 给出 |
| `40101` | 401 | 未登录 / 登录态失效 | 缺令牌、令牌过期 |
| `40301` | 403 | 无权限 | 已登录但角色不够 |
| `40401` | 404 | 资源不存在 | 按 id 查不到（含已软删除） |
| `40901` | 409 | 冲突 | 唯一约束、乐观锁命中 0 行、状态不允许流转 |
| `42901` | 429 | 请求过于频繁 | 同一 IP 的登录尝试超过阈值（20 次/分钟） |
| `50001` | 500 | 服务内部错误 | 非业务错误统一折叠成这个码，真实原因只进日志 |
| `50401` | 504 | 超时 | ctx 截止时间到 |

新增业务码的规则：

- 前三位必须与期望的 HTTP 状态码一致（`40001 → 400`），否则 `errs.Code.HTTPStatus` 会把它归到 500；
- 码值在 `errs` 包里集中定义，不允许在 handler / service 里写字面量数字；
- 同一语义不要新增第二个码，前端的分支是按语义写的。

### 3.1 两条行为约束

码表管的是「失败怎么表达」，下面两条管的是「什么算失败」，前端同样会感知：

- **按身份隔离的资源**：管理员可见全部，其他角色只能看到自己创建的记录——即使请求里带了
  别人的 `owner_id` 也不会放开。越权访问单条记录返回 `40401` 而不是 `40301`：403 等于确认
  「这条 id 存在」，连续试就能数出别人的数据量。前端把 404 一律展示成「记录不存在」即可。
- **登录失败锁定**：同一用户名连续失败 5 次后，15 分钟内一律 `40301`，期间不比对密码；
  登录成功清零。前端不要把 `40301` 只当成「角色不够」，登录页要原样展示 `message`。
- **登录按 IP 限流**：同一 IP 对 `/api/v1/auth/login` 的尝试超过 20 次/分钟返回 `42901`。
  它锁的是调用方（保护 bcrypt 的 CPU），与上面按账号的锁定是两件事——换用户名刷
  不会触发账号锁定，但会触发这一条。计数存放在 `cache` 里，切 Redis 后多实例共享。
- **兜底响应不套信封**：路径不存在是 `404`，路径存在但方法不对是 `405`（带 `Allow` 头），
  两者都是 `text/plain`。它们不代表任何业务接口，所以不参与上面的码表；客户端按
  「看到 405 说明方法写错了」处理即可。

## 4. 分页

请求（`GET` query，`dto.PageQuery`）：

| 参数 | 默认 | 上限 | 说明 |
|---|---|---|---|
| `page` | 1 | — | 从 1 开始，非法值（含非数字）归 1 |
| `page_size` | 20 | 200 | 非法值（含非数字）归默认，超上限截断 |
| `keyword` | 空 | — | 各资源自行解释是否使用 |

响应（`dto.PageResult[T]`，前端 `types/index.ts` 的 `PageResult<T>`）：

```json
{ "list": [], "total": 0, "page": 1, "page_size": 20 }
```

`list` 永远是数组，空结果是 `[]` 而不是 `null` —— 前端不必判空。

## 5. 字段与时间

- **命名**：线上字段一律 `snake_case`，前端 `types` 与后端 `dto` 的 json tag 逐字段对应，
  不允许前端另起更顺手的名字。
- **时间**：一律 `time.Time`，序列化为 RFC3339（`2026-11-10T09:30:00Z`）；
  「业务日期」用 `model.DateOnly` 截到日历日。唯一例外是令牌过期时间 `expires_at`，用 Unix 秒。
- **标识**：主键 `id` 为数字；关联字段带实体名（`owner_id`），不用 `pid` 这类缩写。
- **乐观锁**（可选约定）：更新接口回传读到的 `updated_at` 原值；不传则退化为最后写入者获胜。
- **更新语义**：`PUT` 是全量覆盖——`content` 省略等于清空，而不是「保持原值」。`omitempty`
  只影响序列化，不影响反序列化，所以「没传」与「传空串」在服务端无法区分。
- **永不外泄**：密码、内部 DSN、堆栈不进任何响应体。

## 6. 契约在代码里的锚点

文档会漂移，代码不会。契约要素只有这几个实现点，改的时候对号入座：

| 契约要素 | 后端 | 前端 |
|---|---|---|
| 响应体形状、状态码折叠 | 成功：`apps/server/internal/server/envelope.go`（序列化钩子）；失败：`apps/server/internal/pkg/response/response.go` | `apps/web/src/api/client.ts` |
| 业务码表 | `apps/server/internal/pkg/errs/errs.go` | `apps/web/src/api/client.ts`（`ApiError.code`） |
| 分页参数与形状 | `apps/server/internal/dto/common.go` | `src/types/index.ts` + `src/constants/index.ts` |
| 接口前缀、令牌键 | `apps/server/internal/server/router.go` | `src/constants/index.ts` |
| 鉴权头 | `apps/server/internal/server/middleware/auth.go` | `apps/web/src/api/client.ts` |

## 7. 变更流程

契约是两端共用的，所以它没有「谁先谁后」的自由：一次改动要在同一个提交里闭合。

1. **先改本文档**：形状、码表、字段名先在这里定稿，评审时只看这一份。
2. **再改后端**：`dto` / `errs` / `response`；`internal/dto` 或 `internal/pkg/errs` 的改动
   一律视为契约变更，走本节流程。
3. **同一个提交里改前端**：`src/types/index.ts` 与对应 `src/api/xxx.ts`。
4. **同步两端规范里的摘要**：`apps/server/AGENTS.md` 第 1 节、`apps/web/AGENTS.md` 第 2 节。
   摘要与外链无关，是各自文件里的内联副本，**必须手动跟上**——没有测试抓得到它。
5. **自检**：`task lint`（`go vet` + 前端 `tsc`）。`types` 与 `dto` 对不上会在这里暴露；
   码表行数快速核对：`grep -c '^| `[0-9]' docs/contracts/api.md apps/*/AGENTS.md`，三个数字应当相等。
6. **只在必要时扩展**：不要为「以后可能要用」预留字段，字段一旦上线就不能改名。

不属于契约的改动（内部重构、SQL 优化、样式调整）不需要走这套流程，也不要顺手改本文档。
